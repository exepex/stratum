# Release notes: Stratum 0.3.0

**Not released yet.** These notes collect the changes made on `main` since [0.2.0](0.2.0.md), and are completed
when 0.3.0 is tagged.

[← Documentation home](../README.md) · [Versioning and upgrades](../guides/upgrading.md) ·
[ADR 0028: Version numbers, releases, and publishing only when the owner runs it](../adr/0028-version-numbers-releases-and-publishing.md)

## Breaking changes

No service runs on Stratum yet, so these renamed and removed keys have no compatibility shim and no deprecation entry
in the configuration metadata: an old key is ignored, with no warning, and its setting falls back to Stratum's
default. Search your configuration files, environment variables and Java configuration for each key below.

### The HTTP client's `timeout` is renamed `read-timeout`

**What changed.** The longest wait for the first byte of an answer, and between two of its bytes, has the name Spring
Boot gives it in `spring.http.clients.read-timeout`. Its default stays `5s`.

| 0.2.0 | 0.3.0 |
| --- | --- |
| `stratum.http-client.defaults.timeout` | `stratum.http-client.defaults.read-timeout` |
| `stratum.http-client.clients.<name>.timeout` | `stratum.http-client.clients.<name>.read-timeout` |
| `STRATUM_HTTPCLIENT_DEFAULTS_TIMEOUT` | `STRATUM_HTTPCLIENT_DEFAULTS_READTIMEOUT` |
| `ClientSettings.timeout()` and the builder's `.timeout(..)` | `ClientSettings.readTimeout()` and `.readTimeout(..)` |
| `HttpClientConstants.DEFAULT_TIMEOUT` (internal) | `HttpClientConstants.DEFAULT_READ_TIMEOUT` |

The fix of `SX-HTTPC-1001` now says that Spring Boot's `read-timeout` keeps its name under
`stratum.http-client.clients.<name>`.

**Who is affected.** Services on `stratum-starter-http-client` that set `timeout` for a client or under `defaults`,
or call `timeout()` in an `HttpClientPropertiesCustomizer` or on `stratumHttpClients.settings(..)`.

**Steps.** Rename the key, in `application.properties`:

```properties
stratum.http-client.clients.inventory.read-timeout=3s
```

or in `application.yml`:

```yaml
stratum:
  http-client:
    clients:
      inventory:
        read-timeout: 3s
```

and in Java, call `readTimeout(..)` on the settings' builder. See [HTTP client → Properties](../modules/http-client.md#properties).

### `stratum.web.timeout.status` is removed

**What changed.** The status of a request that ran out of its time limit, `SX-WEB-1007`, is set in
`stratum.web.error.statuses`, as every other code's status is. Its default stays `503`. The component `status` of
`WebProperties.TimeoutSettings` is removed with it.

**Who is affected.** Services on `stratum-starter-webmvc` or `stratum-starter-webflux` that set
`stratum.web.timeout.status`, or `status(..)` on `TimeoutSettings` in a `WebPropertiesCustomizer`.

**Steps.** Move the value, in `application.properties`:

```properties
stratum.web.error.statuses.SX-WEB-1007=504
```

or in `application.yml`:

```yaml
stratum:
  web:
    error:
      statuses:
        SX-WEB-1007: 504
```

and in Java, put `SX-WEB-1007` in the statuses of `properties.error()`. See
[Web: response timeouts](../modules/web-timeouts.md#set-the-limits).

### A failed call of another service carries its own code

**What changed.** A request whose call of a `@StratumClient` interface failed, and that none of your own handlers
answers, still gets `500`, but with a code that says what happened instead of `SX-WEB-1005`:

| The call | 0.2.0 | 0.3.0 |
| --- | --- | --- |
| Got a final error answer, such as `400`, `404` or `500` | `500`, `SX-WEB-1005` | `500`, `SX-HTTPC-0007` |
| Got `429`, `502`, `503` or `504` after its retries | `500`, `SX-WEB-1005` | `500`, `SX-HTTPC-0009` |
| Got an answer whose body cannot be read | `500`, `SX-WEB-1005` | `500`, `SX-HTTPC-0008` |

With it:

- in [backward-compatible mode](../modules/web-compatible-mode.md), the caller gets Stratum's error body for these
  failures instead of Spring Boot's, as it already did for `SX-HTTPC-0001` to `SX-HTTPC-0006`;
- the `error.code` tag of the request's `http.server.requests` timer, and of its span, is the code instead of
  `none`, and the `error.code` field of the log line that carries the exception holds it;
- the failure is logged in one ERROR line from the web module, with the code and its stack trace; on Spring MVC that
  line replaces the servlet container's ERROR line for the failure;
- `DownstreamException` implements `FailureWithErrorCode`, so it gains `getErrorCode()`, `getErrorDetail()` and
  `getReport()`;
- an answer whose body cannot be read is thrown as `UnreadableAnswerException`, a subclass of Spring's
  `RestClientException`, instead of a plain `RestClientException`, so a `catch` of `RestClientException` still
  catches it. A request body that no converter can write still fails with a plain `RestClientException`.

The status stays `500` on purpose: a status such as `503` would make each caller in a chain send the request again.
See [What your caller learns](../guides/what-your-caller-learns.md).

**Who is affected.** Services on `stratum-starter-http-client` whose consumers read `SX-WEB-1005`, or in
backward-compatible mode read Spring Boot's body, for these failures; dashboards or alerts that filter on
`error.code="none"`; and code that checks for exactly `RestClientException`, such as with `getClass()`.

**Steps.** Tell the consumers of the endpoints that call a Stratum client about the new codes. To answer a failure
your own way, catch `DownstreamException` or `UnreadableAnswerException` in your own `@RestControllerAdvice`, which
always wins. To give one of the codes another status, map it, knowing that a status such as `503` makes callers send
the request again:

```properties
stratum.web.error.statuses.SX-HTTPC-0009=503
```

or in `application.yml`:

```yaml
stratum:
  web:
    error:
      statuses:
        SX-HTTPC-0009: 503
```

### `ClientSettings` gains two components

**What changed.** The HTTP client's settings record `ClientSettings` gains the components `errors` and
`operations`, so its constructor takes two more arguments. Its builder and every existing accessor are unchanged.

**Who is affected.** Java configuration that calls `new ClientSettings(...)` with every argument, instead of
`ClientSettings.builder()` or `toBuilder()`.

**Steps.** Build the settings with `ClientSettings.builder()`, or `properties.clientSettings("<name>").toBuilder()`,
as [Configure in Java](../modules/http-client.md#configure-in-java) shows.

## Other changes

### Your own code for another service's error status

**What changed.** A client's `errors` gives an error status of the other service your own error code, at three
levels: `stratum.http-client.defaults.errors`, `stratum.http-client.clients.<name>.errors`, and
`stratum.http-client.clients.<name>.operations.<operation>.errors` for the methods marked
`@StratumOperation("<operation>")`. The operation's code wins over the client's, which wins over the defaults'. A
listed status still throws a `DownstreamException`, whose `getErrorCode()` is your code; your caller gets that code
with the status `stratum.web.error.statuses` gives it, or `500`. Every status you do not list keeps `SX-HTTPC-0007`
or `SX-HTTPC-0009`, and the retries and the circuit breaker are unchanged. A bad entry stops startup with
`SX-CORE-1003`, `SX-HTTPC-1009` or `SX-HTTPC-1010`. See
[Your own code for an error status](../modules/http-client-errors.md#your-own-code-for-an-error-status).

**Who is affected.** Nothing changes for a service that sets no `errors`.

**Steps.** None. To use it:

```properties
stratum.http-client.clients.inventory.errors[409]=ORD-0409
stratum.web.error.statuses.ORD-0409=409
```

or in `application.yml`:

```yaml
stratum:
  http-client:
    clients:
      inventory:
        errors:
          "409": ORD-0409
  web:
    error:
      statuses:
        ORD-0409: 409
```
