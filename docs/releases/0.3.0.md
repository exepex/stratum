# Release notes: Stratum 0.3.0

**Not released yet.** These notes collect the changes made on `main` since [0.2.0](0.2.0.md), and are completed
when 0.3.0 is tagged.

[← Documentation home](../README.md) · [Versioning and upgrades](../guides/upgrading.md) ·
[ADR 0028: Version numbers, releases, and publishing only when the owner runs it](../adr/0028-version-numbers-releases-and-publishing.md)

## Breaking changes

No service runs on Stratum yet, so these renamed and removed keys have no compatibility shim and no deprecation entry
in the configuration metadata: an old key is ignored, with no warning, and its setting falls back to Stratum's
default. Search your configuration files, environment variables and Java configuration for each key below.

### Spring Boot 4.2.0

**What changed.** Stratum moves from Spring Boot 4.1.2 to 4.2.0, with Spring Framework 7.1
([compatibility](../guides/upgrading.md#compatibility)). What your service sees:

- **Your Problem Details keep `instance`.** Spring Framework 7.1 no longer sets `instance` on a `ProblemDetail`
  that your handler returns. Stratum now sets it to the request path, without the query, when your handler leaves
  it empty, in strict and backward-compatible mode, so your error bodies stay as they were. A value your handler
  sets is kept, and Stratum's own error body still has no `instance`
  ([Spring MVC](../../starters/stratum-starter-webmvc/README.md#your-own-error-handling),
  [WebFlux](../../starters/stratum-starter-webflux/README.md#your-own-error-handling)).
- **WebFlux upload limits stay.** Spring Boot 4.2 limits each part of a multipart upload to `1MB` of disk and an
  upload to `50` parts. With the web module on, Stratum keeps `10MB` and `50` in strict mode, and sets both to no
  limit (`-1B` and `-1`) in backward-compatible mode, as before. With `stratum.web.enabled=false`, Spring Boot's
  new limits apply ([Spring's own limits](../modules/web-body-limit.md#springs-own-limits)).
- **Failed exports on this machine stay quiet.** OpenTelemetry 1.68 and Micrometer 1.18 log a failed send under new
  logger names, which Stratum turns off when the export address is on this machine:
  `io.opentelemetry.exporter.otlp.internal.HttpExporter` and `.GrpcExporter` for spans, and
  `io.micrometer.registry.otlp.shaded.io.opentelemetry.exporter.otlp.internal.HttpExporter`
  for metrics, next to `OtlpMeterRegistry`
  ([running without a Collector](../../starters/stratum-starter-observability/README.md#running-without-a-collector)).
- **No long-task timers by default.** Spring Boot 4.2 makes none unless
  `management.metrics.observations.include-active-long-task-timer` is `true`, and no longer reads
  `management.metrics.observations.ignored-meters`. So a workflow's `stratum.workflow.active` timer exists only with
  that key ([workflows](../modules/logging-workflows.md)).
- **More failures are recorded.** Since Spring Framework 7.1, a 5xx that Spring's `ResponseEntityExceptionHandler`
  answers, also in your own subclass of it, marks the request's span as failed and sets its timer's `error` tag
  ([error codes on requests](../modules/observability-traces.md#error-codes-on-requests)).
- **Kafka batch listeners are observed.** A `@KafkaListener` with `batch = "true"` joins its first record's trace,
  and its `spring.kafka.listener` timer has the same tags as a single-record listener instead of `name`, `result`
  and `exception`. Spring Kafka 4.2.0 counts each batch twice in that timer
  ([messages](../modules/observability-messages.md)).
- **An invalid `Accept` header gets `406`.** Spring Framework 7.1 parses the header more strictly, so a value such as
  `text/plain;foo` is refused.
- **Spring Boot's own changes**, from its 4.2 release notes: behind a proxy, `X-Forwarded-Prefix` is ignored unless
  `server.request.header.forwarded.use-prefix=true`; `server.forward-headers-strategy` is deprecated; on Tomcat,
  `Location` headers are relative by default; `RestTemplate` and `RestTemplateBuilder` are deprecated for removal.
- **One advisory less.** OpenTelemetry 1.68.0 fixes
  [GHSA-ccrj-gw8r-854m](https://osv.dev/GHSA-ccrj-gw8r-854m), for which the 0.1.0 notes asked services to set
  `opentelemetry.version` to `1.67.0` ([open advisories](../guides/upgrading.md#open-advisories)).

**Who is affected.** Every service. With `stratum-parent`, it gets Spring Boot 4.2.0 with this release. Under a
company parent on Spring Boot 4.1.x, Stratum logs one `SX-CORE-1005` warning at startup until the parent moves to
4.2. Also affected: a service that sets the old OpenTelemetry logger names to see failed sends, that sets
`ignored-meters`, or whose dashboards read the `name`, `result` or `exception` tag of a Kafka batch listener's timer.

**Steps.** Under a company parent, move it to Spring Boot 4.2.0
([with stratum-bom](../getting-started/with-stratum-bom.md)). Remove the `opentelemetry.version` override, and
`management.metrics.observations.ignored-meters` if you set it. To see failed sends on this machine again, use the
new logger names, in `application.properties`:

```properties
logging.level.io.micrometer.registry.otlp.shaded.io.opentelemetry.exporter.otlp.internal.HttpExporter=error
logging.level.io.opentelemetry.exporter.otlp.internal.HttpExporter=error
```

or in `application.yml`:

```yaml
logging:
  level:
    io.micrometer.registry.otlp.shaded.io.opentelemetry.exporter.otlp.internal.HttpExporter: error
    io.opentelemetry.exporter.otlp.internal.HttpExporter: error
```

### The HTTP client's `timeout` is renamed `read-timeout`

**What changed.** The longest wait for the first byte of an answer, and between two of its bytes, has the name Spring
Boot gives it in `spring.http.clients.read-timeout`. Its default stays `5s`.

| 0.2.0 | 0.3.0 |
| --- | --- |
| `stratum.http-client.defaults.timeout` | `stratum.http-client.defaults.read-timeout` |
| `stratum.http-client.clients.<name>.timeout` | `stratum.http-client.clients.<name>.read-timeout` |
| `STRATUM_HTTPCLIENT_DEFAULTS_TIMEOUT` | `STRATUM_HTTPCLIENT_DEFAULTS_READTIMEOUT` |
| `ClientSettings.timeout()` and the builder's `.timeout(..)` | `ClientSettings.readTimeout()` and `.readTimeout(..)` |
| `HttpClientConstants.DEFAULT_TIMEOUT` (internal) | `HttpClientConstants.DEFAULT_READ_TIMEOUT` |

The fix of `SX-HTTPC-1001` now says that Spring Boot's `read-timeout` keeps its name under
`stratum.http-client.clients.<name>`.

**Who is affected.** Services on `stratum-starter-http-client` that set `timeout` for a client or under `defaults`,
or call `timeout()` in an `HttpClientPropertiesCustomizer` or on `stratumHttpClients.settings(..)`.

**Steps.** Rename the key, in `application.properties`:

```properties
stratum.http-client.clients.inventory.read-timeout=3s
```

or in `application.yml`:

```yaml
stratum:
  http-client:
    clients:
      inventory:
        read-timeout: 3s
```

and in Java, call `readTimeout(..)` on the settings' builder. See [HTTP client → Properties](../modules/http-client.md#properties).

### `stratum.web.timeout.status` is removed

**What changed.** The status of a request that ran out of its time limit, `SX-WEB-1007`, is set in
`stratum.web.error.statuses`, as every other code's status is. Its default stays `503`. The component `status` of
`WebProperties.TimeoutSettings` is removed with it.

**Who is affected.** Services on `stratum-starter-webmvc` or `stratum-starter-webflux` that set
`stratum.web.timeout.status`, or `status(..)` on `TimeoutSettings` in a `WebPropertiesCustomizer`.

**Steps.** Move the value, in `application.properties`:

```properties
stratum.web.error.statuses.SX-WEB-1007=504
```

or in `application.yml`:

```yaml
stratum:
  web:
    error:
      statuses:
        SX-WEB-1007: 504
```

and in Java, put `SX-WEB-1007` in the statuses of `properties.error()`. See
[Web: response timeouts](../modules/web-timeouts.md#set-the-limits).

### A failed call of another service carries its own code

**What changed.** A request whose call of a `@StratumClient` interface failed, and that none of your own handlers
answers, still gets `500`, but with a code that says what happened instead of `SX-WEB-1005`:

| The call | 0.2.0 | 0.3.0 |
| --- | --- | --- |
| Got a final error answer, such as `400`, `404` or `500` | `500`, `SX-WEB-1005` | `500`, `SX-HTTPC-0007` |
| Got `429`, `502`, `503` or `504` after its retries | `500`, `SX-WEB-1005` | `500`, `SX-HTTPC-0009` |
| Got an answer whose body cannot be read | `500`, `SX-WEB-1005` | `500`, `SX-HTTPC-0008` |

With it:

- in [backward-compatible mode](../modules/web-compatible-mode.md), the caller gets Stratum's error body for these
  failures instead of Spring Boot's, as it already did for `SX-HTTPC-0001` to `SX-HTTPC-0006`;
- the `error.code` tag of the request's `http.server.requests` timer, and of its span, is the code instead of
  `none`, and the `error.code` field of the log line that carries the exception holds it;
- the failure is logged in one ERROR line from the web module, with the code and its stack trace; on Spring MVC that
  line replaces the servlet container's ERROR line for the failure;
- `DownstreamException` implements `FailureWithErrorCode`, so it gains `getErrorCode()`, `getErrorDetail()` and
  `getReport()`;
- an answer whose body cannot be read is thrown as `UnreadableAnswerException`, a subclass of Spring's
  `RestClientException`, instead of a plain `RestClientException`, so a `catch` of `RestClientException` still
  catches it. A request body that no converter can write still fails with a plain `RestClientException`.

The status stays `500` on purpose: a status such as `503` would make each caller in a chain send the request again.
See [What your caller learns](../guides/what-your-caller-learns.md).

**Who is affected.** Services on `stratum-starter-http-client` whose consumers read `SX-WEB-1005`, or in
backward-compatible mode read Spring Boot's body, for these failures; dashboards or alerts that filter on
`error.code="none"`; and code that checks for exactly `RestClientException`, such as with `getClass()`.

**Steps.** Tell the consumers of the endpoints that call a Stratum client about the new codes. To answer a failure
your own way, catch `DownstreamException` or `UnreadableAnswerException` in your own `@RestControllerAdvice`, which
always wins. To give one of the codes another status, map it, knowing that a status such as `503` makes callers send
the request again:

```properties
stratum.web.error.statuses.SX-HTTPC-0009=503
```

or in `application.yml`:

```yaml
stratum:
  web:
    error:
      statuses:
        SX-HTTPC-0009: 503
```

### `ClientSettings` gains two components

**What changed.** The HTTP client's settings record `ClientSettings` gains the components `errors` and
`operations`, so its constructor takes two more arguments. Its builder and every existing accessor are unchanged.

**Who is affected.** Java configuration that calls `new ClientSettings(...)` with every argument, instead of
`ClientSettings.builder()` or `toBuilder()`.

**Steps.** Build the settings with `ClientSettings.builder()`, or `properties.clientSettings("<name>").toBuilder()`,
as [Configure in Java](../modules/http-client.md#configure-in-java) shows.

### A Log4j2 service's own Log4j2 configuration stops startup

**What changed.** With Log4j2 as the logging backend, the logging module now refuses a Log4j2 configuration of
the service's own, as it already refused a Logback file with Logback: a Log4j2 file on the class path
(`log4j2.xml`, `log4j2-spring.xml`, their `-test` forms, and the same names ending in `.properties`, `.yml`,
`.yaml`, `.json` or `.jsn`) or `logging.log4j2.config.override` stops startup with `SX-LOGGING-1003`. Such a
file wrote lines in its own layout, which Stratum did not mask. The message names the file or the key, never the
key's value. The fix of `SX-LOGGING-1003` now names Log4j2 files and `logging.log4j2.config.override`. With
Logback, nothing changes: Spring Boot logs with Logback even when Log4j2 is also on the class path, and ignores
a Log4j2 file and the key there. Log4j's own properties that choose a file are still not checked
([#412](https://github.com/exepex/stratum/issues/412)).

**Who is affected.** Services on `stratum-starter-logging` that log with Log4j2 (no Logback on the class path)
and keep a Log4j2 file of their own or set `logging.log4j2.config.override`.

**Steps.** Remove the file and the key. Set levels, a log file and the format with `logging.*` and
`stratum.logging.*` properties, as [Logging → Customize](../../starters/stratum-starter-logging/README.md#customize)
describes. To keep your own configuration, turn the module off with `stratum.logging.enabled=false`.

## Other changes

### Your own code for another service's error status

**What changed.** A client's `errors` gives an error status of the other service your own error code, at three
levels: `stratum.http-client.defaults.errors`, `stratum.http-client.clients.<name>.errors`, and
`stratum.http-client.clients.<name>.operations.<operation>.errors` for the methods marked
`@StratumOperation("<operation>")`. The operation's code wins over the client's, which wins over the defaults'. A
listed status still throws a `DownstreamException`, whose `getErrorCode()` is your code; your caller gets that code
with the status `stratum.web.error.statuses` gives it, or `500`. Every status you do not list keeps `SX-HTTPC-0007`
or `SX-HTTPC-0009`, and the retries and the circuit breaker are unchanged. A bad entry stops startup with
`SX-CORE-1003`, `SX-HTTPC-1009` or `SX-HTTPC-1010`. See
[Your own code for an error status](../modules/http-client-errors.md#your-own-code-for-an-error-status).

**Who is affected.** Nothing changes for a service that sets no `errors`.

**Steps.** None. To use it:

```properties
stratum.http-client.clients.inventory.errors[409]=ORD-0409
stratum.web.error.statuses.ORD-0409=409
```

or in `application.yml`:

```yaml
stratum:
  http-client:
    clients:
      inventory:
        errors:
          "409": ORD-0409
  web:
    error:
      statuses:
        ORD-0409: 409
```

### Timeouts of one operation

**What changed.** A method marked `@StratumOperation("<operation>")` can have its own `read-timeout` and
`total-timeout`, under `stratum.http-client.clients.<name>.operations.<operation>.read-timeout` and
`.total-timeout`. Each one the operation leaves unset is its client's, then the defaults'. The connect timeout, the
pool, `max-wait`, the retries and the circuit breaker stay per client. See
[HTTP client: operations](../modules/http-client-operations.md).

**Who is affected.** Nothing changes for a service that sets neither key.

**Steps.** None. To use it:

```properties
stratum.http-client.clients.reports.operations.monthly-report.read-timeout=20s
stratum.http-client.clients.reports.operations.monthly-report.total-timeout=30s
```

or in `application.yml`:

```yaml
stratum:
  http-client:
    clients:
      reports:
        operations:
          monthly-report:
            read-timeout: 20s
            total-timeout: 30s
```

### Cloud signatures and keys are masked by name

**What changed.** The logging starter's redaction masks, in full, the values under the cloud names `sig` and
`signature` (Azure's SAS `sig`, AWS's `X-Amz-Signature`), `subscription key` (Azure API Management's
`subscription-key` and `Ocp-Apim-Subscription-Key`) and `account key` (Azure Storage's `AccountKey`), as a field, in
text such as `AccountKey=…;` or `Ocp-Apim-Subscription-Key: …`, in the `url` of the HTTP client's call log and in the
query of an outgoing call's span. They were written as sent. A name of yours made of the same words, such as
`signatureAlgorithm` or `accountKey`, is masked too. Generic names such as `key` and `code` are still not masked. See
[Logging → Redaction](../../starters/stratum-starter-logging/README.md#redaction).

**Who is affected.** Services on `stratum-starter-logging` that log values under these names, or call a URL that
carries them.

**Steps.** None. To mask a secret under a generic name, add the name to `stratum.logging.redaction.extra-keys`.

### The client IP behind a proxy that adds a port

**What changed.** An `X-Forwarded-For` entry with a port, such as `203.0.113.7:51234` or `[2001:db8::1]:443`, as
Azure Application Gateway writes it by default, gives the client IP without the port, on both web starters. It was
not read, so the client IP was the proxy's address, or, on Spring MVC with `server.forward-headers-strategy=native`,
missing. See [Web: the client IP](../modules/web.md#the-client-ip).

**Who is affected.** Services on `stratum-starter-webmvc` or `stratum-starter-webflux` behind a proxy that adds a
port. Nothing changes for an entry without one.

**Steps.** None.
