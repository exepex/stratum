## Breaking changes

### A database failure gets 503 or 409 instead of 500

**What changed.** With `stratum.backward-compatible=false`, the default, a request that fails
because of the database, and that none of your own `@ExceptionHandler` methods answers, no longer
gets `500` and `SX-WEB-1005` in every case:

| The failure | 0.1.0 | 0.2.0 |
| --- | --- | --- |
| A statement timeout, a wait for a pooled connection, a lock timeout, a deadlock or a transaction that ran out of time | `500`, `SX-WEB-1005` | `503`, `SX-WEB-1010` |
| A duplicate key, or a row another request changed since it was read | `500`, `SX-WEB-1005` | `409`, `SX-WEB-1011` |

The full list is in [Database failures](../modules/web-database-errors.md). A `409` is now logged
at WARN with its stack trace; a `503` at ERROR, as the `500` was. With the data JPA starter, which
0.2.0 publishes for the first time, a statement Stratum cancels at its time limit
(`SX-DATA-1003`) is answered with `503` too.

**Who is affected.** Services on `stratum-starter-webmvc` or `stratum-starter-webflux` with
`stratum.backward-compatible=false` whose consumers check for `500` on these failures. A service
in backward-compatible mode sees no change.

**Steps.** To keep `500`, map each code back:

```properties
stratum.web.error.statuses.SX-WEB-1010=500
stratum.web.error.statuses.SX-WEB-1011=500
stratum.web.error.statuses.SX-DATA-1003=500
```

or in `application.yml`:

```yaml
stratum:
  web:
    error:
      statuses:
        SX-WEB-1010: 500
        SX-WEB-1011: 500
        SX-DATA-1003: 500
```

To give a failure your own answer instead, handle its exception in your own
`@RestControllerAdvice`, which always wins.
