# Release notes: Stratum 0.2.0

**Not released yet.** These notes collect the changes made on `main` since
[0.1.0](0.1.0.md), and are completed when 0.2.0 is tagged.

[← Documentation home](../README.md) · [Versioning and upgrades](../guides/upgrading.md) ·
[ADR 0020: Version numbers and releases](../adr/0020-version-numbers-and-releases.md)

## Breaking changes

### A database failure gets 503 or 409 instead of 500

**What changed.** With `stratum.backward-compatible=false`, the default, a request that fails
because of the database, and that none of your own `@ExceptionHandler` methods answers, no longer
gets `500` and `SX-WEB-1005` in every case:

| The failure | 0.1.0 | 0.2.0 |
| --- | --- | --- |
| A statement timeout, a wait for a pooled connection, a lock timeout, a deadlock or a transaction that ran out of time | `500`, `SX-WEB-1005` | `503`, `SX-WEB-1010` |
| A duplicate key, or a row another request changed since it was read | `500`, `SX-WEB-1005` | `409`, `SX-WEB-1011` |

The full list is in [Database failures](../modules/web-database-errors.md). A `409` is now logged
at WARN with its stack trace; a `503` at ERROR, as the `500` was. With the data JPA starter, which
0.2.0 publishes for the first time, a statement Stratum cancels at its time limit
(`SX-DATA-1003`) is answered with `503` too.

**Who is affected.** Services on `stratum-starter-webmvc` or `stratum-starter-webflux` with
`stratum.backward-compatible=false` whose consumers check for `500` on these failures. A service
in backward-compatible mode sees no change.

**Steps.** To keep `500`, map each code back:

```properties
stratum.web.error.statuses.SX-WEB-1010=500
stratum.web.error.statuses.SX-WEB-1011=500
stratum.web.error.statuses.SX-DATA-1003=500
```

or in `application.yml`:

```yaml
stratum:
  web:
    error:
      statuses:
        SX-WEB-1010: 500
        SX-WEB-1011: 500
        SX-DATA-1003: 500
```

To give a failure your own answer instead, handle its exception in your own
`@RestControllerAdvice`, which always wins.

### A started Spring MVC response's statements end by its time limit

**What changed.** 0.1.0 documented that a response that has started is never cut off by its time
limit. The web module still never cuts it off, but with the data JPA starter, which 0.2.0 publishes
for the first time, every SQL statement of a web request ends by the request's limit minus
`stratum.data.deadline-margin` (150ms by default). On Spring MVC that holds for a response that has
started too, until the limit passes: a statement that starts within the margin of the limit fails
with `SX-DATA-1003`. After the limit, a started response reads no limit. See
[Downloads and streams](../modules/web-timeouts.md#downloads-and-streams).

**Who is affected.** Services on `stratum-starter-webmvc` with a data starter whose downloads or
streams read the database for longer than their request's limit.

**Steps.** Give each such endpoint its own limit, or none:

```properties
stratum.web.timeout.routes[/exports/**]=0
```

or in `application.yml`:

```yaml
stratum:
  web:
    timeout:
      routes:
        "[/exports/**]": 0
```

or `@ResponseTimeout(0)` on its controller method.

### The main pool is named `main` in its metrics, timeouts and log lines

**What changed.** With a data starter, Stratum names Spring Boot's HikariCP pool `main` when the
service gave it no name, in both modes, since metrics are internal
([ADR 0010](../adr/0010-modules-on-when-present-and-one-compatibility-switch.md)). Each place that
named the pool now shows that one name:

| Where | 0.1.0 | 0.2.0 |
| --- | --- | --- |
| The `pool` tag of HikariCP's metrics, such as `hikaricp.connections.active` | `HikariPool-1` | `main` |
| The `pool` tag of `stratum.data.timeouts` | `dataSource` | `main` |
| The `SX-DATA-1003` message in the log | `on data source dataSource` | `on pool main` |
| The TLS check's WARN | `The data source 'dataSource' ...` | `The data source 'main' ...` |

See [Pool names](../modules/data-named-pools.md#pool-names).

**Who is affected.** Services whose dashboards, alerts or log searches filter on
`pool="HikariPool-1"` or `pool="dataSource"`, or on the old text of these lines.

**Steps.** Filter on `pool="main"` instead. To keep a name of your own, set it:

```properties
spring.datasource.hikari.pool-name=orders
```

or in `application.yml`:

```yaml
spring:
  datasource:
    hikari:
      pool-name: orders
```

### All pools together may open at most 30 connections

**What changed.** Once every bean exists, Stratum adds up the `maximum-pool-size` of every pool,
the main pool included, and stops startup with `SX-DATA-1005` when the total is above
`stratum.data.max-connections`, 30 by default. See
[The cap on connections](../modules/data-named-pools.md#the-cap-on-connections).

**Who is affected.** Services whose main pool's `spring.datasource.hikari.maximum-pool-size` is above
30, or whose own HikariCP pool beans add up to more.

**Steps.** Raise the cap to at least the total the message names:

```properties
stratum.data.max-connections=50
```

or in `application.yml`:

```yaml
stratum:
  data:
    max-connections: 50
```

### The main pool lends a connection at the first statement

**What changed.** With a data starter, Stratum sets Spring Boot's
`spring.datasource.connection-fetch=lazy` in both modes: Spring Boot's `dataSource` lends a pooled
connection at a transaction's first statement, not when the transaction begins. A transaction that
runs no statement borrows nothing. With `spring.jmx.enabled=true`, Spring Boot then no longer
registers the main pool as an MBean. See the [property table](../modules/data.md#properties).

**Who is affected.** Services that read the main pool's MBean, and code that expects a connection to
be held from the start of a transaction. A named pool reached by its qualifier is not affected.

**Steps.** For the MBean, set `spring.datasource.hikari.register-mbeans=true`. To borrow at the
start of each transaction again:

```properties
spring.datasource.connection-fetch=eager
```

or in `application.yml`:

```yaml
spring:
  datasource:
    connection-fetch: eager
```

### The health check leaves out routing data sources

**What changed.** The data JPA starter sets Spring Boot's
`management.health.db.ignore-routing-data-sources=true` in both modes, so the `db` health check
checks each pool and no routing data source over them.

**Who is affected.** Services with a routing data source of their own whose `/actuator/health`
output, or a check reading it, expects that data source's entry.

**Steps.** To keep it:

```properties
management.health.db.ignore-routing-data-sources=false
```

or in `application.yml`:

```yaml
management:
  health:
    db:
      ignore-routing-data-sources: false
```

## Other changes

### Repositories on a pool

**What changed.** With the data JPA starter, `stratum.data.sources.<name>.packages` or
`@UseDataSource("<name>")` puts Spring Data JPA repositories on a named pool, through one entity
manager factory. A transaction stays on the pool of its first repository call; a call for another
pool fails with `SX-DATA-1008`. A mapping that breaks a rule stops startup with `SX-DATA-1007`, and
open-in-view in a servlet application with `SX-DATA-1009`. With a mapping, a plain `DataSource` is
the routing data source `stratumRoutingDataSource`, the one primary `DataSource`
([ADR 0022](../adr/0022-routing-data-source-is-the-only-primary.md)). See
[Repositories on a pool](../modules/data-named-pools.md#repositories-on-a-pool).

**Who is affected.** Services that map repositories. Nothing changes for a service that maps none.

**Steps.** None.

### Named pools

**What changed.** `stratum.data.sources.<name>.*` adds HikariCP pools beside Spring Boot's, each
with its own beans, which only a qualifier reaches, its own settings, time limits and transaction
manager. The database health check and the pool metrics list every pool. See
[Named pools](../modules/data-named-pools.md).

**Who is affected.** Services that need a second pool, such as for batch work. Nothing changes for a
service that sets no `stratum.data.sources` key.

**Steps.** None.

### Each SQL statement gets a span in a sampled trace

**What changed.** With a data starter and the observability starter, each SQL statement that runs
in a sampled trace gets a client span named after its operation, such as `SELECT`, with the
database system and name, and the pool's name. It carries no SQL text, value or table name, and
adds no meter. See
[Query spans](../modules/data-query-spans.md).

**Who is affected.** Services with a data starter and tracing. Their sampled traces hold one more
span per statement, which their trace backend stores; a request that runs many statements adds
many spans.

**Steps.** None to keep working. To keep fewer, lower `management.tracing.sampling.probability`.
