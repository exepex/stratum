# Release notes: Stratum 0.2.0

**Not released yet.** These notes collect the changes made on `main` since
[0.1.0](0.1.0.md), and are completed when 0.2.0 is tagged.

[← Documentation home](../README.md) · [Versioning and upgrades](../guides/upgrading.md) ·
[ADR 0020: Version numbers and releases](../adr/0020-version-numbers-and-releases.md)

## Breaking changes

### A database failure gets 503 or 409 instead of 500

**What changed.** With `stratum.backward-compatible=false`, the default, a request that fails
because of the database, and that none of your own `@ExceptionHandler` methods answers, no longer
gets `500` and `SX-WEB-1005` in every case:

| The failure | 0.1.0 | 0.2.0 |
| --- | --- | --- |
| A statement timeout, a wait for a pooled connection, a lock timeout, a deadlock or a transaction that ran out of time | `500`, `SX-WEB-1005` | `503`, `SX-WEB-1010` |
| A duplicate key, or a row another request changed since it was read | `500`, `SX-WEB-1005` | `409`, `SX-WEB-1011` |

The full list is in [Database failures](../modules/web-database-errors.md). A `409` is now logged
at WARN with its stack trace; a `503` at ERROR, as the `500` was. With the data JPA starter, which
0.2.0 publishes for the first time, a statement Stratum cancels at its time limit
(`SX-DATA-1003`) is answered with `503` too.

**Who is affected.** Services on `stratum-starter-webmvc` or `stratum-starter-webflux` with
`stratum.backward-compatible=false` whose consumers check for `500` on these failures. A service
in backward-compatible mode sees no change.

**Steps.** To keep `500`, map each code back:

```properties
stratum.web.error.statuses.SX-WEB-1010=500
stratum.web.error.statuses.SX-WEB-1011=500
stratum.web.error.statuses.SX-DATA-1003=500
```

or in `application.yml`:

```yaml
stratum:
  web:
    error:
      statuses:
        SX-WEB-1010: 500
        SX-WEB-1011: 500
        SX-DATA-1003: 500
```

To give a failure your own answer instead, handle its exception in your own
`@RestControllerAdvice`, which always wins.

### A started Spring MVC response's statements end by its time limit

**What changed.** 0.1.0 documented that a response that has started is never cut off by its time
limit. The web module still never cuts it off, but with the data JPA starter, which 0.2.0 publishes
for the first time, every SQL statement of a web request ends by the request's limit minus
`stratum.data.deadline-margin` (150ms by default). On Spring MVC that holds for a response that has
started too, until the limit passes: a statement that starts within the margin of the limit fails
with `SX-DATA-1003`. After the limit, a started response reads no limit. See
[Downloads and streams](../modules/web-timeouts.md#downloads-and-streams).

**Who is affected.** Services on `stratum-starter-webmvc` with a data starter whose downloads or
streams read the database for longer than their request's limit.

**Steps.** Give each such endpoint its own limit, or none:

```properties
stratum.web.timeout.routes[/exports/**]=0
```

or in `application.yml`:

```yaml
stratum:
  web:
    timeout:
      routes:
        "[/exports/**]": 0
```

or `@ResponseTimeout(0)` on its controller method.
