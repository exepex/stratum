## Findings

**1. BLOCKING (R1): the ADR leaves out owner-agreed details.** `gap-review-merged.md` records these decisions.
The ADR does not contain them (checked by grep at `0331c35`):
- A8 (00:19Z): "no new attempt under ~100ms left". Not in ADR 4.4.
- A9 (00:21Z): "`copy-headers` with nothing to copy sends nothing". Not in the ADR.
- B3 (00:30Z): "a second 401 fails, logged once per client per minute; token-relay 401 passed back unchanged". Not in
  ADR 3.3.
- Backoff: ST-ENG-51 requires "backoff with jitter", and `design-v4.md:18` says "200ms first wait, then doubles with
  jitter, max 2s". The ADR says only `retry-delay 200ms` (ADR 2.4).

**Fix:** add each line to the named ADR section (3.3, 2.1 or 3.4, 4.4, and 4.3 or 2.4).

**2. SHOULD FIX (R5): POST and PATCH retry wording is ambiguous.** ADR 4.2 lists "a dropped connection before any
answer" as retried. It then says "POST and PATCH are retried only when nothing was sent". A connection dropped after the
request was written, for example a server that closes before answering, is a case where something was sent. ST-ENG-51
says retrying a non-idempotent write is a bug, and only a write never sent may be retried. As written, an implementer
could retry a POST that the server already processed. The spike's stale-connection case (`NoHttpResponseException`,
`spike-result.md`) is a real route to it.

**Fix:** state that for POST and PATCH only a connect failure, where nothing was written, is retried. A connection
dropped after the request was written is not.

**3. SHOULD FIX (ST-AG-17): `AGENTS.md:222` states the old ST-ENG-34 wording.** It reads "a typed
`stratum.<module>.*` property, or Spring Boot's own key where Boot has one". For the HTTP client, Boot's
`spring.http.serviceclient.*` keys do not apply (ST-ENG-34 exception). The Claims' dependent search covered rule IDs
and the ST-ENG-51 wording, so this line was missed. The rule file is the one agents read first.

**Fix:** add "(except the HTTP client starters, ADR 0011)" to `AGENTS.md:222`, or name the reason the line stays.

**4. SHOULD FIX (ST-DOC-08): the owner's span decision has no issue.** Owner decision 00:54Z: span query values are
masked like the logs. ADR 8.2 says this is "a separate observability item", but no issue is named and the "to file"
list in the ADR's follow-up items leaves it out. Today `stratum-starter-observability/README.md:111` says the full URL,
query string included, is kept on the span. ST-SEC-03 allows the query on the call log only, so this is a known
violation that the design says to fix and does not track.

**Fix:** add "mask query values on HTTP client span URLs (owner, 00:54Z; ST-SEC-03)" to the "to file" list in
ADR "Follow-up items". The coordinator opens the issue.

**5. MINOR: a rule example names a key the ADR does not have.** `engineering.md:192` uses
`stratum.http-client.pool.max-size` as an example of a startup error. The ADR's key is
`stratum.http-client.clients.<name>.max-connections`. The example was already in the base; this PR makes it stale.

**Fix:** use a key that exists, or a generic example such as `stratum.<module>.<key>`.
