## 1. The project in one paragraph

Stratum is an SDK on Spring Boot 4.1.2 and Java 25, built with Maven. GroupId and package root
are `com.exepex.stratum`. It gives microservices auto-configured components: logging,
observability, web, HTTP clients, security, cloud and Testcontainers testing. Teams then add a
starter, set `stratum.*` properties and write only business code.

The repo layout:
- `platform/`: bom, build parent, rules and the service parent.
- `libs/`: core, test, web, and so on.
- `starters/`

Every module is OFF until `stratum.<module>.enabled=true` (`@ConditionalOnStratumModule`,
ADR 0003). The rules for every agent are in `AGENTS.md` and the six topic files under
`docs/agents/`. Read all of them before any work and say in each PR that you did.

## 2. How Aashish works: rules that are firm

- **Never merge.** Aashish (GitHub `contactexepex`) merges every PR. Never push to `main`.
- **One judge per PR**, unless he asks for two. The implementer never judges its own work.
  Ask the coordinator for the judge with the PR number and head commit.
- **Check every judge or bot finding critically.** Fix only what is valid and realistic, with no
  over-engineering. Decline the rest on the thread, with evidence.
- **A valid finding that arrives after its PR merged** gets its own small PR with one judge.
- **Never break an existing service's API contract** with its consumers. Business comes first,
  and consumers can take 6 to 12 months to migrate.
- **MVC and WebFlux always behave the same, and correctly.** Each must give the same status and
  error for the same case, in every mode. When they differ, fix whichever stack is wrong; MVC is
  not automatically the reference.
- **stratum-core never contains web-related dependencies.**
- **Prefer metrics over logs.** No unnecessary log lines, because log quota costs money.
- **Questions go one at a time.** Ask one question, close it, then ask the next.
  - Each question needs a plain explanation, a concrete example, every option and your pick.
  - When he shares raw thoughts, review them first: gaps, questions, pushback.
  - Discussing a design is not approval to build it. Build only after he says go.
- **No unrequested tooling.** No size-check scripts or CI jobs, and no plans written into the
  repo.
- **File limits.** 400 lines for code and configuration, 500 for text. Split a file before it
  goes over. Never squeeze lines to fit.
- **Every PR:**
  - The body uses the Claims template from `docs/agents/judge.md`: request, requirements with
    evidence, broken-code proof, not done, files read, line counts.
  - Start the body with `<!-- Generated by Claude Code -->` and "Requested by: Aashish
    (contactexepex)".
  - Assign it to `contactexepex` and subscribe to its activity.
  - Run the full `./mvnw verify` before asking for the judge.
- **Key policy:**
  - Use Boot's own keys where Boot has one; `stratum.*` only for what Boot lacks.
  - Every setting is configurable from files and from Java (`XxxPropertiesCustomizer` in
    `META-INF/spring.factories`) and has IDE metadata.
  - Each starter README has one complete copy-paste example with every key.
- **Virtual threads** are never on by default. Teams opt in with `spring.threads.virtual.enabled`.
- **Sonar.** Sessions cannot reach sonarcloud.io, so ask him for screenshots.
- **How to answer him.** Simple, precise and short, never verbose. Lead with the result or the
  one decision you need. When a message is unclear, check what he means before building (for
  example, on 2026-11-02 "fix that issue" meant PR #106, not issue #107).
- **Not every gap is a blocker.** He may say to open a GitHub issue and come back later; then
  open one short issue with the gap, the options and our pick, and build nothing.

## 2b. Code, naming and test style (firm)

- KISS and SOLID; no class with only one or two small methods (ST-ENG-16); merge small classes;
  one job per class; no abstraction without a second use.
- Descriptive names, never generic ones such as first/last; property keys short and grouped,
  with the full sentence in the IDE description.
- Streams over loops, builders, statics only in utilities and factories, constructor injection,
  Lombok and MapStruct for boilerplate; reuse maintained Apache-compatible libraries.
- Java configuration wins over properties. A team's own bean always wins
  (`@ConditionalOnMissingBean`).
- Tests: no unnecessary tests; add one only when a real gap would let a bug through. Prove each
  new test fails on broken code (reproduce first, then fix). Shared starter test helpers live in
  `stratum-test` (test scope).
- Javadoc rules apply only to Stratum's own code. Keep Boot's plugin versions.

## 3b. Public API (ADR 0009, built 2026-11-02)

- `com.exepex.stratum.core.api.StratumInternal` (CLASS retention) marks every public type services
  must not use. A public type without it is API. No class moved, so no package cycle was added.
- An API type exposes only API types. `PublicApiRule` in `stratum-test` checks this in every
  starter's and library's architecture test: supertypes, type parameters and bounds, public and
  protected members (inherited ones too), throws clauses, and protected nested types.
- No package cycles anywhere (ST-ENG-57); internal types of core or the base library may be used by
  modules, never another starter's types.
- **Open, issue #107, before 0.1.0:** a new public type whose author forgets the label silently
  becomes API. Options: A an API list per module, B `@StratumApi` on API types plus one rule that
  every public type carries exactly one label and ADR 0010 (recommended), C the judge checks it.
  Aashish: not a blocker, deal with it later.
- **Still to build for 0.1.0:** the japicmp or Revapi API check that ignores labelled types
  (ADR 0009 decision 7). Resolve #107 first, because that check trusts the labels.

## 4. Compatible mode: what was built

The setting is `stratum.web.backward-compatible`. It defaults to `true`, which is compatible
mode. `false` is the Stratum standard, and the project template sets it. Compatible mode is
permanent and frozen: it gets no new features, and removing it in a major version was rejected.
The user page is `docs/modules/web-compatible-mode.md`.

**Error bodies (#95):**
- Errors that Spring or Boot answers keep Spring Boot's body and media type.
- Boot's body follows the team's `spring.web.error.include-*` settings exactly. Stratum strips
  nothing.
- When `include-stacktrace` or `include-exception` is on, Stratum logs ONE WARN at every startup
  calling it a security leak. There is no per-response WARN, no off switch and no new key, and the
  docs show no way to silence it. Aashish: false positives are the team's call, handled in their
  monitoring. The bean deliberately has no `@ConditionalOnMissingBean`.
- Stratum's standard body (`application/problem+json`) is sent instead in these cases:
  - The consumer sends `Accept: application/problem+json`, named explicitly with q above 0. A
    wildcard does not count.
  - The failure is a `StratumException` or another `FailureWithErrorCode`. That includes a coded
    cause under a wrapper that has no status of its own.
  - The failure is a timeout or a body over the limit, even when wrapped.
  - The setting is `false`.
- No IDs are added to Boot's body; `X-Correlation-Id` is on every response. IDs are still added
  to the service's own `ProblemDetail`.
- A browser always gets Stratum's reference page, with the trace ID as its reference. API and
  browser are told apart by the Accept header. A team's own `templates/error/*.html` still wins.

**Limits (#96):** in compatible mode Stratum adds no limit at all:
- no default timeout (10s in standard mode);
- no default body limit (256KB in standard mode);
- no WebFlux multipart defaults (10MB per part, 50 parts). This was Aashish's option A.

A limit the team sets always applies. The code is `WebProperties.defaultTimeout()`,
`defaultBodyLimit()` and `WebFluxEnvironmentPostProcessor`.

**Startup line and counter (#97):**
- `BackwardCompatibleModeReport` logs the INFO line and the WARN.
- The counter is `stratum.web.requests.without.standard.errors` (`BootErrorBodyCounter`).
  - Its tag is `route` (`WebConstants.ROUTE_TAG`), with `UNKNOWN` for an unknown path. A static resource's `/**` is treated
    as unknown.
  - micrometer-core is optional, in stratum-web only.
- The documented "safe to switch" query uses `max_over_time(...) > 0`, not `increase()`, because a
  series starts at its first count.
- No caller tag yet: it needs a verified caller, so it belongs to the security module's work.
- No `Deprecation` or `Sunset` headers: Aashish ruled compatible mode is not a deprecation.
- `RequestRouteInterceptor` runs first (#99), so a request a team's interceptor rejects is counted
  under its route. A request a filter rejects before matching is `UNKNOWN` on both stacks.

**Parity (#98):** Boot's WebFlux `DefaultErrorAttributes` reads the status only from
`ResponseStatusException` or `@ResponseStatus`. Stratum's WebFlux `StratumErrorAttributes` now
takes it from any `ErrorResponse`. The IT error cases were compared on both stacks; the only gaps
were 405 and the coded-failure browser page, both added on WebFlux.
An unlisted status, such as 499, gets Spring MVC's phrase `Http Status 499` on WebFlux too.
Aashish chose option A (21:20Z): both stacks answer an unlisted status such as 499 with that
status, in both modes. Boot's MVC `AbstractErrorController.getStatus` answers 500 for it, so
`ErrorBodyAdvice` (JSON) and `ReferenceErrorPage` (HTML) set the status line from the body's
`status`. Stratum's Problem Details title is `ErrorResponseFactory.reasonPhraseOf`, which gives
`Http Status 499` for an unlisted status, as Boot's MVC body does.

**Trace ID (#101):** WebFlux reads MDC on a Reactor thread, so the WebFlux starter sets
`spring.reactor.context-propagation=auto` whenever the web module is on (the team's value wins).
Without the observability module, both stacks now carry the trace ID. Neither carries
`correlationId` then, because the observability module's `CorrelationIdRecorder` puts it in MDC.

### 5a. HTTP client (#79 H1, then H2 to H4)

The plan was approved 2026-10-31 and is on hold until the module review finishes.

- **Starters.** `stratum-starter-http-client` (RestClient on Apache HttpClient 5) and
  `stratum-starter-reactive-http-client` (WebClient on Reactor Netty) share
  `libs/stratum-http-client`.
- **Settings.**
  - Spring's `spring.http.clients.*` and `spring.http.serviceclient.<group>.*` keys win.
  - `stratum.http-client.*` covers only the extras.
  - Defaults: connect 2s and read 5s, through StratumDefaults; `pool.max-connections` 50 and
    `pool.max-wait` 2s.
  - Pool gauges exist on the reactive client only.
- **Boot 4.1.2 bug.** WebClient HTTP interface groups lose their own timeouts and SSL. The
  workaround `WebClientGroupSettings` is in #79, with a test that fails once Boot fixes it.
- **H2, headers.**
  - Forward `traceparent` and `X-Correlation-Id`.
  - Other headers go out only through an allow list (`forward-headers`).
  - Authorization, Cookie, Set-Cookie, Proxy-Authorization and X-Api-Key are never forwarded,
    and listing one fails startup.
- **H3, errors.**
  - `DownstreamUnavailableException` gets SX-HTTPC-0001 (timeout, 504) or SX-HTTPC-0002
    (connect, 503).
  - The HTTP client library adds these defaults to `stratum.web.error.statuses`, so the web
    module needs no change.
  - 4xx and 5xx from the downstream service stay Spring's.
- **H4, call log.** `stratum.http-client.call-log=none|errors|all`, default `errors`, which
  writes one WARN per failed call. Never log headers or bodies.

## 6. Useful facts

- **Build.** In a cloud container, install JDK 25 with
  `apt-get install -y openjdk-25-jdk-headless`, then run `./mvnw verify`.
  - Use `-pl <module> -am` while working.
  - Run the full verify before asking for a judge.
  - Install `libs/stratum-core` again after switching branches, or `stratum-test`'s
    error-code test fails on a stale jar.
- **Before a push**, read the log for `BUILD SUCCESS`; a pipeline's exit code can hide a failed
  build. `pkill -f maven` also kills a shell whose own command line contains "maven".
- **Records.** Judge verdicts (`reviews/judge/`) and probes (`reviews/probes/`) live in the old project's shared folder, not in the repo; the merged PR bodies on GitHub hold each change's Claims.
- **Git.** `git push --force-with-lease` worked on this session's own `claude/...` branches
  (#101), so rebasing a pushed branch of your own is possible. Never rewrite someone else's branch.
- **Boot 4.1.2 web facts.**
  - The error keys are `spring.web.error.*`, not `server.error.*`.
  - `ErrorAttributeOptions.of()` omits the status.
  - Tomcat's error dispatch runs after the tracing scope closed, so MVC keeps the IDs on the
    request (`RequestIdsFilter`).
